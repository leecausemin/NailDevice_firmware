4. 앱 굽기

cd /c/Users/user/Desktop/CM_Lab/2026_summer/firmware/erm_frimware && bash flash.sh


빌드 결과 HEX 위치

우리 링커 스크립트(ble_app_uart_gcc_nrf52.ld: FLASH ORIGIN = 0x27000)와 일치한다.

(JY_TP_IMU_DFU_Test_0x26000.hex)는 앱 베이스가 0x26000이라 그 패키지를 통째로
구우면 이렇게 된다. 이 상태에서 우리 앱을 구우면 SoftDevice가 0x26000으로
점프하는데 우리 앱은 0x27000에 있으므로 아예 부팅하지 않는다.
RTT에 한 글자도 안 나오고 광고도 안 뜬다. 2026-08-05 10:37/10:39의
rtt_bmi160_restored*.log가 0바이트인 것이 이 증상이다.

⚠️ flash.sh는 이걸 스스로 못 고친다. SoftDevice 재설치가 else 가지에만 있는데
   nrfjprog --program은 앱 주소가 어긋나도 "성공"으로 끝나므로 그 가지에
   절대 들어가지 않는다. diag_build_flash.bat도 flash.sh만 부르므로 마찬가지다.
   SoftDevice가 틀렸으면 위 2~4번을 손으로 실행할 것.


========================================
IMU 미검출 진단 - 확정된 사실 (2026-08-05 최종)
========================================

★ CHIP_ID=0x00과 0xFF는 같은 뜻이다. 여기서 시작할 것.

   sdk_config.h의 NRFX_SPIM_MISO_PULL_CFG = 1 = PULLDOWN 이다.
   그래서 MISO가 떠 있으면 SPIM 경로(bmi160_spi_read_hw)는 항상 0x00을 읽는다.
   비트뱅 경로(bb_read_reg_at)는 NOPULL이라 같은 조건에서 0xFF를 읽는다.

   즉 로그마다 0xFF와 0x00이 섞여 나온 것은 센서 상태가 달라서가 아니라
   읽는 코드 경로가 달라서다. 두 값 모두 "아무도 MISO를 구동하지 않음"
   하나만 가리킨다.

   ⚠️ 이 때문에 예전 진단의 다음 추론들이 전부 무효다. 다시 세우지 말 것:
      - "0xFF가 아니라 0x00이니 MISO가 한 번도 HIGH로 안 올라갔다" → 아니다
      - "라인이 LOW로 눌려 있다 vs 장치가 없다"를 0x00으로 가른다  → 못 가른다
      - "0x00이 계속 나오니 8MHz가 너무 빨라서다"                  → 근거 없음
      - 전기 진단(풀업/풀다운 읽기)의 FLOAT 결과                    → 정보 없음
        (CS가 비활성이면 정상 BMI160도 SDO를 high-Z로 두므로 FLOAT다)


펌웨어는 용의선상에서 제외됐다 (2026-08-05 실측)

  다음을 모두 08-04 19:05에 CHIP_ID=0xD1 + FIFO 실데이터가 나온 조건과
  동일하게 맞춘 뒤에도 CHIP_ID는 0x00이었다:

    - 프로파일    DUAL_ERM_PWR5 (P0.05 HIGH), 핀 27/25/19/14
    - 전송        SPIM0, 8MHz, mode3, MSB first
    - 전원 시퀀스 핀을 출력으로 구동 → EN=LOW 100ms → EN=HIGH 50ms
    - 0x7F 더미 리드로 SPI 모드 진입, mode3/mode0 양쪽 시험

  로그: rtt_csfix_20260805.log, rtt_seq20260804_repro_20260805.log


굽고 있는 칩은 ERM 보드가 맞다 (DK 오굽기 아님)

  nrfjprog -f nrf52 --memrd 0x10000100 --n 20
    INFO.PART    = 0x00052840   nRF52840
    INFO.VARIANT = 0x41414430   AAD0
    INFO.PACKAGE = 0x00002005   CKxx = WLCSP  ← ISP1807 모듈
    INFO.RAM     = 0x100        256KB
    INFO.FLASH   = 0x400        1024KB

  DK(PCA10056)에 박힌 nRF52840은 aQFN73이라 INFO.PACKAGE가 0x2000으로 나온다.
  0x2005면 WLCSP = ISP1807 모듈 = ERM 보드다. 이 한 줄로 매번 확정할 수 있다.

  이 보드의 FICR DEVICEADDR = F7681282 6CBD34C1
    → BLE random static address = F4:C1:F7:68:12:82
    폰 스캐너에 이 MAC으로 잡히면 지금 굽는 칩이 광고하는 칩과 같은 것이다.


IMU2 테스트는 무효다

  IMU2(SPI1 30/31/2/29)로 CHIP_ID=0x00이 나왔지만(rtt_imu2_probe_20260805.log),
  이 디바이스에는 IMU가 한 개뿐이다. 없는 핀을 찔러본 것이므로 근거가 아니다.
  원본 펌웨어가 SPI1까지 초기화하는 것은 2-IMU 보드용으로 쓰였기 때문이다.


★ 원본 펌웨어 실행 중 레지스터 덤프 (2026-08-05) — 가장 신뢰할 수 있는 자료

  ERM_Sync_V2_1 + SD 6.0.0을 실제로 굽고, 돌아가는 상태에서 SWD로 읽었다.
  정적 디스어셈블 추정이 아니라 실행 중 하드웨어 상태다.

    SPIM0 (IMU1) @0x40003000
      ENABLE     = 0x07          SPIM 사용
      PSEL.SCK   = 0x1B = 27
      PSEL.MOSI  = 0x19 = 25
      PSEL.MISO  = 0x13 = 19
      PSEL.CSN   = 0xFFFFFFFF    → 소프트웨어 CS (드라이버에 안 맡김)
      FREQUENCY  = 0x80000000    → 8 MHz
      CONFIG     = 0x06          → CPOL=1 CPHA=1 MSB first = mode 3
      RXD.MAXCNT/AMOUNT = 2, TXD.MAXCNT/AMOUNT = 1  → 레지스터 1개 읽기 형태

    SPIM1 (2-IMU 보드용, 이 디바이스엔 센서 없음)
      SCK=30 MOSI=31 MISO=2, CSN 미사용, 8MHz, mode3

    GPIO P0
      OUT = 0x68004020   → P0.05 HIGH, P0.14 HIGH(CS idle), P0.27 HIGH(SCK idle),
                            P0.29/P0.30 HIGH (IMU2쪽)
      DIR = 0xFE004020   → P0.05 출력, P0.14 출력, P0.25~P0.31 출력, P0.19는 입력
      PIN_CNF[5]  = 0x03 → 출력 (입력버퍼 차단)
      PIN_CNF[14] = 0x03 → 출력 (CS)
      PIN_CNF[19] = 0x04 → 입력 + PULLDOWN (MISO)
      PIN_CNF[23] = 0x02 → 입력, 버퍼 차단 (IMU_INT1 미사용)

  여기서 확정되는 것:

  1. 우리 펌웨어의 SPI 설정은 처음부터 옳았다.
     핀 27/25/19/14 + 소프트웨어 CS + 8MHz + mode3가 원본과 완전히 같다.
     클럭·모드·핀맵을 다시 의심하지 말 것.

  2. ★ P0.05는 출력으로 HIGH다. 원본 펌웨어가 P0.05를 건드린다.
     "이미지에 P0.05를 set/clear하는 코드가 없다"는 이전 결론은 틀렸다
     (정적 디스어셈블에서 못 찾았을 뿐이다. 테이블/루프 초기화로 보인다).
     → BOARD_DUAL_ERM_PWR5(P0.05 사용)가 옳은 프로파일이다.
     → 정적 분석으로 "코드가 없다"를 결론내지 말 것. 실행 중 레지스터가 답이다.

  3. 원본도 MISO에 PULLDOWN을 건다. 우리 쪽 0x00 판독은 정상 동작이다.

========================================
다음에 할 일 — 펌웨어가 아니라 계측
========================================

MCU는 디버거(DK debug-out)에서 전원을 받아 계속 돌지만, 센서 레일과 ERM 모터는
보드 자체 전원(배터리/부스트)에서 나올 가능성이 높다. 그러면 배터리가 방전돼도
BLE는 멀쩡하고 IMU만 죽는다 — 지금 증상과 정확히 같다.
"08-04 저녁엔 되다가 다음 날 아침부터 계속 안 된다"도 이것과 잘 맞는다.

테스터로 순서대로 잴 것:

  1. 배터리 전압 (보드 전원 스위치 ON 상태)
  2. TPS7A02 입력 전압
  3. TPS7A02 출력 = 센서 VDD    ← P0.05를 HIGH로 둔 상태에서
  4. P0.05 자체의 전압          ← 3.3V 근처로 올라오는지
  5. 2~4를 "DK 케이블만 연결 / 보드 자체 전원도 ON" 두 조건에서 각각

  3번이 안 올라오면 IMU가 응답할 방법이 없다. 그게 확인되면 펌웨어는 더 볼 것이 없고
  전원 경로(배터리 → 부스트 → LDO → 센서 VDD)를 따라가면 된다.

또 하나 시도해볼 것:

  보드를 물리적으로 완전히 전원 차단(배터리 분리 + USB 분리)하고 30초 뒤 켜기.
  BMI160은 VDD 상승 시점의 CSB 레벨로 인터페이스를 정하고, 한번 I2C로 굳으면
  소프트 리셋(0xB6)으로도 재시도로도 안 풀린다. 오직 진짜 POR만 푼다.
  디버거가 붙어 있으면 모듈 전원이 유지돼 POR이 아예 안 일어날 수 있다.

미해결로 남은 것 (원인 미규명)
- imu_diag_sweep() 호출 시 보드가 그 안에서 멈춘다. ENABLE_UNSAFE_IMU_DIAG_SWEEP=0.
- IMU_DIAG_ELECTRICAL=1로 두면 진단 출력 뒤 더 진행하지 못한다. 현재 0.
  (다만 위 ★ 항목대로 이 진단의 FLOAT 결과 자체가 정보가 없으므로 우선순위 낮음)


========================================
현재 소스 상태 (2026-08-05)
========================================

- BOARD_FORCE_PROFILE = BOARD_DUAL_ERM_PWR5
    08-04에 0xD1이 나온 유일한 조건. 이 #define을 지우면 자동 탐색이 복원되지만
    자동 탐색은 NAIL 후보에서 P0.23을 출력으로 구동하고, 그 핀은 ERM에서
    IMU_INT1(센서가 구동하는 출력)이라 푸시풀끼리 맞붙는다. ERM만 다룰 때는 고정.

- BMI160_SPI_FREQUENCY = 8MHz, mode3 (mode0 자동 폴백 있음)
    8MHz는 유일하게 FIFO 자체검사를 통과한 값이다. 1MHz는 성공 이력이 없다.

- BMI160_BOOT_POWER_CYCLE_BRANCH = 0
    lsm6_pins_init()의 BMI160 전용 전원 사이클 분기를 꺼서 08-04와 같은
    LSM6 경로(핀 구동 → EN LOW 100ms → EN HIGH 50ms)를 타게 했다.
    1로 켜면 SPI 4핀 high-Z + 500ms 부팅 대기 버전이 살아난다. 켜기 전에
    08-04 시퀀스로 0xD1이 재현되는지부터 확인할 것.

- imu_bus_release()가 CS를 놓지 않고 풀업 입력으로 둔다
    복구 상태기계가 레일을 내릴 때 CSB가 뜨면 BMI160이 I2C로 굳는다.
    이번 증상의 원인은 아니었지만 데이터시트상 명백한 요구사항이라 그대로 둔다.
    nrf_gpio_cfg_default(IMU_CS)로 되돌리지 말 것.
